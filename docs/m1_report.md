## 已交付与正确性

已实现单线程 C++20 内存撮合核心：限价、市价 IOC、归属撤单、完整确定性事件与快照；生产版 map/list/hash 与独立 vector 参考模型；trace、重放、逐命令差分和失败缩减。未预建网络、并发或内存池框架。

本地 Debug / ASan+UBSan 各 59 项、Release 60 项测试通过；固定种子长验证为 100 × 10,000 = 1,000,000 条逐命令比较。手工期望错误、生产成交价错误以及远程 CI 错误均实际注入并恢复；2,000 条失败输入缩减为 2 条，永久纳入回归。报告工具对七类损坏证据非零退出，整次运行缺失也不能被跳过。

[同一实现的 PR CI](pr_ci_evidence.md) 已下载核验实际 checkout 与测试数；[独立干净 checkout](clean_checkout.md) 完成首次依赖下载、60 项测试、fixture、2,000 条对拍及两次短基准。复现执行者为独立 Codex 子代理，未声称是真人或另一台硬件。最终合并 SHA 和 main 的独立 push CI 见 [M1 release](https://github.com/Owenqi666/low-latency-matching/releases/tag/m1-baseline)。

## 测量环境和方法

Apple M5 Pro，18 物理核 / 18 逻辑核，48 GiB 内存；macOS 26.6.2 / arm64，虚拟机标志 `kern.hv_vmm_present=0`。Apple clang 21.0.0 (clang-2100.1.1.101)、CMake 4.4.4、Ninja 1.13.2、Python 3.14.8；Release `-O3 -DNDEBUG -std=c++20`，sanitizer OFF。GoogleTest 1.17.0 的下载 SHA-256 固定。

每种场景使用 C=1,000 / 10,000、100,000 条预生成命令，每种模式五轮。参考验证和独立预热在前；每轮重建引擎并执行相同 setup。latency 只包围 process（含结果生成）；throughput 单独计时批量 process 和逐事件全字段消费。解析、文件写入、快照与参考比较均在计时外。所有轮次保留，不减时钟常数。详见 [方法](benchmark_method.md)。

没有锁定线程亲和性、CPU 频率、睿频或专用核。测量期间代理构建与其他基准已停止，但系统背景负载和调度仍未受控。RSS 是含解析、参考验证和预热的进程峰值，不能当作撮合簿独占内存。

时钟名义表示单位为 1 ns，但实测最小正间隔为 41 ns，连续读时钟的 p50 为 0 ns，p99 为 42 ns。双读时钟并记录 duration 的批量均值为 24.71–26.93 ns；单次读时钟并存储为 12.06–14.06 ns。

## 实际负载组成

起始簿为 C/2，最多 64 个工作单；大部分背景订单不成交。这里比较不同保留容量和背景簿规模，不是接近满簿压力测试。配置价格域为 1–20,000；背景买价 9,000–9,015、背景卖价 11,000–11,015（sweep/clustered 无背景卖单）。逐份输入核对的实际工作限价范围为 mixed 10,000–10,031、cancel_heavy 10,000–10,015、sweep/clustered 10,000–10,022。容量、配置域、背景价带、生成周期、种子和初态在原始 workload.json / run_manifest.json；精确工作价带及对应输入 hash 汇入[补充负载 manifest](benchmarks/workload_manifest.json)，保留原始测量文件不变。

| --- | --- | ---: | ---: | --- |
| mixed | 50000 / 16667 / 33333 / 0 | 33334 | 0.000% | 500→500 / 5000→5000 |
| cancel_heavy | 48780 / 0 / 48781 / 2439 | 0 | 2.439% | 500→499 / 5000→4999 |

cancel_heavy 中的 2,439 次 UnknownOrder 是独立标识的错误撤单子场景；成功与失败撤单分开统计。该场景没有成交，不能将其吞吐叫作成交吞吐。mixed 包含部分限价成交、市价和撤单。

sweep 每次市价最多扫 64 单、8 个价位、产生 66 个事件；clustered 每次最多扫 32 单、4 个价位、产生 34 个事件，随后集中撤余单。两者只测买方主动吃卖簿；正确性测试另覆盖反向。sweep 的命令约 98.46% 为增加限价单，因此需单看市价条件分布：

## 原始证据与复现

完整证据包保留正式输入、setup、逐命令 CSV、每轮快照、时钟、环境和验证记录，以及报告修复前的全部八组五轮测量。早期提交 `2ffc508` 的测量保留在 `m1-pre-report-fix/`，正式 `59a2931` 在 `m1-final/`；重新测量是为将交付绑定到已修复的汇总器，不是选择最快结果。两次使用相同撮合/基准二进制哈希，轮间和批次间波动不能解释成引擎优化收益。

[下载 M1 证据包](https://github.com/Owenqi666/low-latency-matching/releases/download/m1-baseline/m1-evidence.tar.gz)，文件级 SHA-256 见 [结果索引](benchmarks/m1_result_index.json)，压缩包校验值见 [归档索引](benchmarks/archive.json)。保存后可先验证已有样本：

```sh
tar -xzf m1-evidence.tar.gz
python3 scripts/summarize_bench.py m1-evidence/m1-final
```

重新测量使用 README 的四场景命令。新机器的耗时不必相同，但输入 hash、事件计数、校验和与规范化末态应相同。独立 checkout 的两次 smoke 已实际验证这一点；这是同一台机器上的独立执行，并非跨硬件性能复现。

## 范围与下一阶段

M1 没有输入队列、网络 RTT、开环到达率、并发、崩溃恢复或持久化指标。C+4 完整输出缓冲使单次 process 同步完成；M2 若接入有限下游队列，需要显式可暂停执行和输出背压，不能丢弃输出后继续接纳命令。设计取舍见两份 ADR；学习路径见 [walkthrough](learning.md)。
